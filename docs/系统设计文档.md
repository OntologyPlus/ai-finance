# 系统设计文档

---

## 一、系统定位

面向集团企业的**财经管理 AI 原生一体化系统**。以"本体驱动（Ontology-Driven）+ 大模型工具调用（Tool-Use）"为核心：业务概念先在本体中结构化定义（对象 / 关系 / 行为 / 规则 / 场景 / 实例），运行时由单一 FinanceAgent 绑定 18 个 Skill 包、调用 **42** 个工具完成跨域任务。系统覆盖**预算编制 / 费用报销 / 审批 / 预警 / 经营分析 / 报表 / PDCA 复盘 / 现金流 / 零基预算 / 研发管线 / HCP 合规 / 场景规划**等全流程。

### 设计原则

1. **本体先行**：所有业务概念先在 ontology/ 下结构化定义（12 个核心模块 + 5 份 CFO 方法论），AI 通过 OAG（Ontology-Augmented Generation）获取确定性上下文
2. **Skill 动态组合**：用户意图 → 场景语义匹配 → 激活 1~3 个 Skill → 合并 activated_objects/rules/behaviors → Agent 执行
3. **工具原子化**：42 个工具覆盖全业务域，每条规则只管一跳，复合效果由 LLM + 工具链组装
4. **幻觉可控**：4 策略检测（事实锚定 / 数值验证 / 关系验证 / 上下文充分性），5% 数值容差；硬规则 token 预算 1500，裁掉 HR-* 则拒答
5. **事件驱动**：16 种领域事件 → EventBus → 4 类内置订阅者（审计 / Write-Back / 一致性告警 / 实时预警）
6. **权限纵深**：字段级 + OBAC + ABAC 三层，AI 权限 L1-L4 四级；关键写路径叠加 SoD（提交人 ≠ 终审人 / 响应人 ≠ 闭环确认人）
7. **可演化的认知层**：24 个 services（RAG / 语义缓存 / 知识库 / 谱系 / 主动顾问 / 查询改写等）支持系统持续学习
8. **图是投影**：实例 CRUD 增量 upsert / tombstone；`OntologyGraphQuery` 只打 GraphStore Protocol，FinanceAgent 不持有 Neo4j driver
9. **决策可追溯**：报销提交/终审/核销、预警闭环、授予/B→A/调拨等引擎成功或阻断路径落 Decision；无预算 ID 提交被 HR-001 拦住并记 `outcome=blocked`

### 2.2 Supervisor 状态机流程

```
用户输入
  │
  ▼
[1] GuardrailsNode: 安全检查（违规 → blocked）
  │
  ▼
[1.5] SemanticCache: 命中则直接返回（记录 cache_hit / similarity）
  │
  ▼
[2] ClassifyNode: 意图分类（15 类 intent → agent_name 映射）
  │
  ▼
[2.5] SlotExtractionNode: 槽位提取（低置信度时覆盖 intent）
  │
  ▼
[3] Router: 单一 Agent 节点 或 多 Agent 串联节点
  │   ├─ 普通意图 → _agent_node（执行对应 Agent）
  │   └─ 跨域意图 → _multi_agent_node
  │       · impact_query   → [budget, expense, alert]
  │       · scenario_query → [budget, analysis, general]
  │       · analysis_query → [analysis, report, alert]
  │
  ▼
[4] ReflectNode: Self-Reflection 循环（最多 3 轮，失败/不完整自动重试）
  │
  ▼
[5] HallucinationCheckNode: 4 策略幻觉检测（事实/数值/关系/上下文）
  │   ├─ should_refuse → 附加拒绝说明
  │   ├─ !is_safe      → 附加待验证提示
  │   └─ is_safe       → 保留原 response
  │
  ▼
[6] SemanticCache.set: 写入语义缓存（response > 10 chars）
  │
  ▼
[7] 指标采集: cache_hits / multi_agent_runs / agent_failures / latencies
  │
  ▼
返回 AgentState（含 response / multi_agent_responses / hallucination_safe / cache_hit 等）
```

### 3.5 规则体系

**硬规则（Hard Rules）**：`HardRuleEngine` 实现 HR-001～HR-035，共 35 条。写路径上作为**确定性门闩**执行（不依赖 LLM）；违反即 `BLOCK`，并记 `Decision.outcome=blocked`。复合诊断/组装仍由 LLM + 原子规则完成。

| 规则 ID | 名称 | 检查逻辑 |
|--------|------|---------|
| HR-001 | 支出必须有对应预算 | 报销必须挂载有效 `budget_id`；缺失则拒绝提交 |
| HR-002 | 预算核销不可超额 | write_off_amount ≤ available_amount |
| HR-003 | 预警触发≠超支许可 | 预警已触发不得当作批准放行 |
| HR-004 | 先批后用(A类预算) | A 类必须先有预先审批 |
| HR-005 | 双签闭环(业务+财经BP) | 业务 BP 与财经 BP 均已签认 |
| HR-008 | 跨象限调拨须管委会批准 | 跨象限调拨不得自行执行 |
| HR-013 | 预警闭环必须双签 | 整改方案与确认人不得为同一人（与 SoD 叠加） |

其余 HR-006～HR-007、HR-009～HR-012、HR-014～HR-035 覆盖税务、管委会比例、里程碑、现金流、情景、HCP、管线等；完整清单见 `ontology/rules/hard_rules.py`。

**软规则（Soft Rules）**：建议性，违反产生警告（`soft_rules.yaml` 声明式配置）

| 规则 ID | 名称 | 检查逻辑 |
|--------|------|---------|
| SR-007 | 预算执行率预警 | 执行率 > 80% 时建议关注 |
| SR-008 | 预警响应时效 | 预警超过 24h 未响应建议升级 |
| SR-011 | 预算编制完整性 | 未编制的 L1 科目建议补充 |

**推理规则（Reasoning Rules）**：业务诊断型规则（`diagnosis_rules.yaml`），用于业务诊断引擎的根因推断。

### 3.7 OAG 上下文注入

`OntologyContextInjector.build_context()` 根据 Skill 的 activated_* 构建 6 类结构化上下文：

```python
async def build_context(
    target_object_ids,      # activated_objects → inject_object()
    activated_rules,        # activated_rules   → inject_rule()
    activated_behaviors,    # activated_behaviors → inject_behavior()
    target_relation_names,  # → inject_relation()
) -> OAGContext:
    # 1. 注入对象定义（名称/类别/属性/参与关系）
    # 2. 注入规则定义（类型/条件/约束）
    # 3. 注入行为定义（前置条件/副作用）
    # 4. 注入关系路径（对象间可达路径）
    # 5. 注入聚合关系（对象的关联对象集合）
    # 6. 优化窗口（按 relevance_score 裁剪到 max_tokens）
```

注入后 prompt 模板示例：

```
[原始 system prompt]

## 本体上下文
[Ontology 上下文注入]
【对象】预算项目 (ID: obj_budget_item)
类别: budget
定义: ...
关键属性: amount, remaining_amount, quadrant
参与关系: rel_strategic_to_budget, rel_budget_to_expense

【规则】支出必须有对应预算 (ID: HR-001)
类型: hard
定义: 任何支出必须挂载到有效的预算项目，无预算不得支出

【行为】A 类冻结 (ID: fin.budget.a_class_freeze)
定义: ...
前置条件: 对象=budget_item, 状态=已批准, 类别=A 类
副作用: 状态→已冻结, 可用额度=0
[/Ontology 上下文注入]
```

OAG 对硬规则另设 **1500 token 预算**。超出预算被裁掉的 HR-* 记入 `truncated_hard_rules`；幻觉检测看到该字段即 `should_refuse`，避免合规底线被静默漏检。实例路径查询走 `GraphStore.shortest_paths`；定义层 `inject_path` 仍按关系定义走第一跳出边。

### 3.8 GraphStore 投影（MySQL SoT）

图不是第二套事实库。MySQL 实例表是 SoT；图是查询投影。

| 组件 | 职责 |
|------|------|
| `GraphStore` Protocol | `upsert_node` / `upsert_edge` / `tombstone_*` / `neighbors` / `shortest_paths` / `as_of` |
| `MemoryGraphStore` | 进程内实现；**读路径始终走 Memory** |
| `Neo4jGraphStore` | 可选远程；边类型统一 `:RELATED`，本体类型写在 `rel_type`；Cypher 参数化；跳数白名单 1..8 |
| `DualWriteGraphStore` | 写 Memory 再写远程；远程失败入 pending 队列；队列 > 5000 则从 Memory 全量重同步。队列为进程内，非持久 outbox |
| `OntologyGraphQuery` | 只打 Protocol；FinanceAgent **不持有** Neo4j driver |

启动：`main.py` → `init_graph_store` → `hydrate_from_instances`（幂等 upsert，**禁止** `DETACH DELETE` 全量删图）。实例 CRUD 增量投影；删除走 tombstone。Neo4j `find_paths` 当前委托 `shortest_paths`，能力弱于 Memory。

`ProvenanceEntry`（P0）定义了哈希链 schema，**尚未**统一 Event / Audit / Lineage 存储。

### 3.9 Decision 一等对象

`DecisionRecord` 是事后审计对象，不同于 `DecisionSandboxEngine`（事前试运行）。

写入：`DecisionRecorder.emit_decision` → MySQL `decision_record` + 图投影（`:Decision`，边 `BASED_ON` / `APPLIED_POLICY` / `CAUSED`）。启动时从 MySQL hydrate 到图。

**已接线的引擎 SoT**（API 与 Agent 工具共用）：报销提交/核销、审批终态、预警响应/闭环/升级、A/B 授予、B→A、调拨执行。HR-001 在提交时由 `HardRuleEngine.execute` 执行：无/无效预算 → 拒绝写入，`outcome=blocked`。

查询 API：

- `GET /api/decisions/{id}`
- `GET /api/decisions/{id}/chain`
- `POST /api/decisions/search`（精确 category + rule-set 先例）
- `GET /api/decisions/explain/expense/{id}`

未做：向量相似先例、独立 PolicyEngine（写门闩继续用 HardRule + SoD，不另加一层 dict matcher）。

## 四、Agent 架构

### 4.1 总体设计

采用 **Supervisor + FinanceAgent + 18 Skills** 三层架构：

- **Supervisor**：状态机驱动的多 Agent 编排器，负责意图分类 / 槽位提取 / 单/多 Agent 路由 / 反思 / 幻觉检测 / 指标采集
- **FinanceAgent**：业务 Agent，42 工具，按意图绑定一个 Skill 作为主 Skill；不持有图数据库连接
- **Skill**：领域知识源，运行时按场景动态选择 1~3 个 Skill 合并上下文

### 4.5 Self-Reflection 循环

```python
async def _reflect_node(state):
    response = state.get("response", "")
    should_continue = (
        not response or len(response.strip()) < 10
        or response.startswith("[LLM调用失败]")
        or response.startswith("[流式调用失败]")
        or "请提供更多" in response
        or "需要更多信息" in response
    )
    if should_continue and state.get("reflection_count", 0) < 3:
        state["reflection_count"] += 1
        return await self._agent_node(state)  # 重试
    return state
```

### 7.3 Write-Back 引擎

```
事件 → _write_back_trigger → WriteBackEngine.execute()
                                ├── budget_system_handler (STRONG)
                                │     核销/冻结/释放 → Cache-Aside 更新 remaining_amount
                                ├── message_system_handler (EVENTUAL)
                                │     预警触发 → 按级别发送通知（站内信/邮件/短信/电话）
                                └── report_system_handler (EVENTUAL)
                                      数据变更 → 标记报表待重新生成
```

**双模式一致性**：
- **STRONG**：同步执行 + 重试，适用于核销→预算系统
- **EVENTUAL**：异步执行，适用于预警→消息系统
- **死信队列**：重试 3 次失败后移入死信队列

### 8.1 三层权限模型

### 8.4 职责分离（SoD）

写路径在硬规则之外叠加 `SoDEnforcer`（`ontology/sod.py`）：同一用户不能在同一资源上同时担任冲突角色。当前闸门包括：

- 报销发起人 ≠ 最终审批人
- 预警响应人 ≠ 闭环确认人（对齐 HR-013）
- 调拨发起人 ≠ 调拨最终审批人

违例抛 `SoDViolation`，操作阻断。SoD 是硬规则的工程封装，不是第二套规则引擎。

## 十一、幻觉检测

### 11.1 4 策略

| 策略 | 方法 | 检测内容 |
|------|------|---------|
| 事实锚定 | `verify_fact_anchoring()` | AI 输出是否引用有效 Ontology 来源标识 |
| 数值验证 | `verify_numerical_claims()` | 数值声明是否与 ontology_data 匹配（5% 容差） |
| 关系验证 | `verify_relation_claims()` | 声称的关系是否存在于 Ontology 中 |
| 上下文充分性 | `check_context_sufficiency()` | 注入的上下文块数量是否足够；**硬规则被裁则直接拒答** |

### 11.2 检测流程

```python
def check_hallucination(ai_output, ontology_data=None):
    context_blocks = len(self._last_oag_context.blocks)
    truncated_hard_rules = list(self._last_oag_context.truncated_hard_rules or [])
    result = guard.check(ai_output, ontology_data, context_blocks, truncated_hard_rules)
    # truncated_hard_rules 非空 → should_refuse（合规底线漏检）
```

### 11.3 在 Supervisor 中的处理

```python
if hallucination_result.should_refuse:
    state["response"] = f"{response}\n\n⚠️ [AI输出置信度不足] {refusal_reason}..."
    state["hallucination_safe"] = False
elif not hallucination_result.is_safe:
    state["response"] = response + "\n\n⚠️ [部分信息待验证] 请以系统实际数据为准。"
    state["hallucination_safe"] = False
else:
    state["hallucination_safe"] = True
```

```
  → [如果趋势下降] detect_anomalies(period="2024-06")
```

```
用户: "项目 A 撤资影响有多大？"
  → impact_query → 多 Agent 串联:

     · expense_reimbursement: 受影响报销
     · alert_monitor: 触发的预警
```

### 16.3 关键技术决策

1. **ECharts 防护三件套**：所有 21 处 ReactECharts 调用加 `notMerge={true} lazyUpdate={true} showLoading={!dataReady}`，规避 undefined 数据导致的 `Cannot read 'push' of undefined` 崩溃
2. **confidence 字段防护**：所有 `confidence.toFixed(...)` 调用包裹 `Number(x ?? 0).toFixed(...)`，规避 FastAPI 序列化 Numeric(5,2) 为 string 后的 `.toFixed is not a function` 崩溃
3. **SSE 流式消费**：`services/stream.ts` 实现流式响应 + 图表消息识别
4. **React Query 5**：服务端状态缓存 + 自动重试 + 失效管理
5. **Zustand 5**：轻量全局状态（用户/主题/通知）
