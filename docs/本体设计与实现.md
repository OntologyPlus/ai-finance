# 本体设计、实现与业务支撑

---

## 一、设计理念

AI 时代的业务语义本体，职责只有一条：**清晰地定义对象、关系、行为与规则**。真正的推理——规则的选取、组装与套用——交还给大语言模型自身的推理能力。

- **本体只管定义**：用清晰、无歧义、带业务语义的方式，说清楚有哪些对象、它们在什么场景下有什么关系、能发生哪些行为、规则是什么
- **大模型负责推理**：面对具体情境，由它匹配场景、挑出相关的对象/关系/规则、灵活组装成推理链、给出结论

## 二、五层本体架构

### 2.1 架构总览

```
┌──────────────────────────────────────────────────────────────┐
│                      场景层 (Scene)                           │
│  11个业务场景 + 语义匹配算法，每个场景声明激活子集              │
├──────────────────────────────────────────────────────────────┤
│                      规则层 (Rule)                            │
│  硬规则15条 + 软规则20条 + 推理规则5条 = 40条                  │
├──────────────────────────────────────────────────────────────┤
│                      行为层 (Behavior)                        │
│  22种行为，结构化前置条件+副作用，支持自动校验与执行            │
├──────────────────────────────────────────────────────────────┤
│                      关系层 (Relation)                        │
│  15条关系 + 实例化机制 + 基数强制执行                          │
├──────────────────────────────────────────────────────────────┤
│                      对象层 (Object)                          │
│  20个核心对象 + 类型继承 + 生命周期状态机 + 实例化机制          │
└──────────────────────────────────────────────────────────────┘
        ↕ 实例层 (Instance) — 运行时对象/关系实例
        ↕ 事件层 (Event) — 16种领域事件驱动
        ↕ 图查询层 (Graph Query) — BFS路径发现+聚合查询
```

| 对象 | 状态列表 | 初始状态 | 关键转换 |

**类型继承**：L1→L2→L3 三级科目形成继承链，子类型自动继承父类型的属性和管控规则。

**设计要点**：
- 每个对象必须有一句**自然语言定义**——比形式正确性更重要
- 关键属性包含**业务语义**（如"战略意图L1"而非"field_01"）
- 对象声明它**参与哪些关系**，大模型据此构建推理路径
- 生命周期状态机让对象自描述其合法状态转换

### 2.3 关系层 — 15条关系 + 实例化机制

每条关系携带**基数约束**、**置信度**、**来源**、**双向关系**标记。运行时通过**关系实例化机制**创建具体的关系实例，并**强制执行基数约束**。

| 关系 | relation_id | 源→目标 | 基数 | 置信度 | 来源 | 双向 |
|------|------------|--------|------|--------|------|------|
| 挂载 | rel_mount | 报销单→预算项目 | N:1 | 1.0 | 人工 | — |
| 对标 | rel_benchmark | 预算项目→战略举措 | N:1 | 1.0 | 人工 | ↔驱动 |
| 归属 | rel_belong | 预算项目→象限 | N:1 | 1.0 | 人工 | — |
| 管控 | rel_control | L3科目→报销单 | 1:N | 1.0 | 系统推断 | — |
| 触发 | rel_trigger | 预算项目→预警记录 | 1:N | 0.9 | 系统推断 | — |
| 响应 | rel_respond | 中心BP→预警记录 | N:1 | 1.0 | 系统推断 | — |
| 确认 | rel_confirm | 预算管理部→预警记录 | N:1 | 1.0 | 系统推断 | — |
| 升级 | rel_escalate | 预警记录→管委会 | N:1 | 0.85 | 系统推断 | — |
| 冻结 | rel_freeze | 预算项目→预算项目 | 1:1 | 1.0 | 系统推断 | ↔释放 |
| 释放 | rel_release | 预算项目→预算项目 | 1:1 | 1.0 | 系统推断 | ↔冻结 |
| B→A转换 | rel_b2a_convert | 预算项目→预算项目 | 1:1 | 1.0 | 人工 | — |
| 审批组织线 | rel_approval_org | 报销单→中心BP | N:1 | 1.0 | 系统推断 | — |
| 审批法人线 | rel_approval_legal | 报销单→预算管理部 | N:1 | 1.0 | 系统推断 | — |
| 裁决 | rel_adjudicate | 管委会→预算项目 | 1:N | 1.0 | 人工 | — |
| 驱动 | rel_drive | 战略举措→预算项目 | 1:N | 1.0 | 人工 | ↔对标 |

**基数强制执行**：

| 基数 | 规则 | 违反示例 |
|------|------|---------|
| 1:1 | 源和目标各最多1条关系 | 一个预算项目不能同时冻结两个其他项目 |
| N:1 | 每个源最多1条关系，多个源可指向同一目标 | 一个报销单只能挂载一个预算项目 |
| 1:N | 每个目标最多1条关系，一个源可有多个目标 | 一个L3科目管控多个报销单 |
| N:N | 无限制 | — |

**关系实例化**：`RelationInstance` 模型记录具体的关系实例（如"报销单#EXP-001 挂载到 预算项目#BUD-2024-001"），支持 `valid_from`/`valid_to` 时间语义。

**结构化模型**：

```python
class Precondition(BaseModel):
    type: str          # field_check / relation_exists / status_in / rule_passed
    target: str        # 对象/关系/规则ID
    condition: str     # 如 "status == 'approved'"

class SideEffect(BaseModel):
    target_type: str   # 如 "obj_budget_item"

    value_source: str  # 如 "param.annual_amount"

```

## 三、OAG 架构：本体增强生成

### 3.1 架构定位

OAG（Ontology-Augmented Generation）是将本体知识注入 LLM 的架构，解决"大模型不知道业务规则"的核心问题。

```
用户请求 → 场景匹配(关键词+语义) → 激活对象/关系/规则子集 → 注入Prompt → LLM推理 → 幻觉检测 → 输出
```

### 3.2 上下文注入 — OntologyContextInjector

4种注入策略，按优先级排列：

| 策略 | 注入内容 | 相关度 | 适用场景 | 实现方式 |
|------|---------|--------|---------|---------|
| OBJECT | 单个对象定义（名称/类别/定义/属性/关系） | 1.0 | 查询特定对象 | 直接查找对象ID |
| RELATION | 单条关系定义（名称/源/目标/语义/场景条件） | 0.9 | 理解对象间关系 | 按名称或ID查找关系 |
| PATH | 对象间关系路径（最大深度5） | 0.8 | 多跳推理 | 沿关系链线性遍历 |
| AGGREGATE | 对象的所有关联关系聚合 | 0.7 | 全局理解 | 遍历所有关系收集关联对象 |

**窗口优化**：按相关度降序排列，裁剪到 max_tokens（默认4000）以内。

### 3.3 幻觉检测 — OntologyHallucinationGuard

4项检测策略：

| 策略 | 检测内容 | 通过条件 | 改进点 |
|------|---------|---------|--------|
| 事实锚定 | AI输出中的Ontology来源标识是否真实存在 | 有效来源≥80% | — |
| 数值验证 | AI输出的数值声明是否与本体数据一致 | 可验证数值≥70% | 上下文关键词匹配+5%容差，减少假阳性 |
| 关系验证 | AI声称的关系是否在Ontology中存在 | 全部有效 | — |
| 上下文充分性 | 注入的上下文块数量 | ≥2块为充分 | — |

**数值验证改进**：提取数值声明时同时提取上下文关键词，仅在字段名匹配时做精确比对（5%容差），字段名不匹配的数值标记为"无法验证"而非"验证通过"。

**拒答机制**：4项平均置信度低于0.6时，设置 `should_refuse=True`。

### 3.4 Skill 融合 — 1 Agent + N Skills 动态组合

**FinanceAgent 是执行引擎，Skill 是领域知识源**。运行时 FinanceAgent 通过 `match_scene_semantic()` 动态选择 1~3 个 Skill，合并其 instructions/activated_objects/activated_rules/activated_behaviors 注入上下文。

```
用户请求
  │
  ▼
Orchestrator（安全检查 + 意图分类）
  │
  ▼ 统一路由到 FinanceAgent

  │
```

## 四、权限体系

### 4.1 四层权限

| 层次 | 机制 | 说明 |
|------|------|------|
| 字段级 | 8种角色 × 3类对象 | 管委会见全部，员工见最少 |
| OBAC | 归属推导+层级推导 | 6种数据范围，支持中心→部门层级推导 |
| ABAC | 结构化条件规则 | 10种操作符，6条默认规则 |
| AI分级 | L1-L4 | AI权限矩阵6场景×6角色 |

### 4.2 ABAC结构化规则引擎

支持10种操作符：`>` / `>=` / `<` / `<=` / `==` / `!=` / `in` / `not_in` / `between` / `contains`

**6条默认结构化规则**：

| 规则ID | 名称 | 字段 | 操作符 | 值 | 动作 |
|--------|------|------|--------|-----|------|
| ABAC-S001 | 大额支出CFO审批 | amount | > | 500000 | require_approval |
| ABAC-S002 | 超期费用不可报销 | days_since_expense | > | 90 | block |
| ABAC-S003 | 预警超时自动升级 | hours_since_alert | > | 48 | auto_escalate |
| ABAC-S004 | 跨中心数据不可见 | center_id | != | (user_center) | hide |
| ABAC-S005 | 预算执行率超限 | execution_rate | >= | 1.1 | require_approval |
| ABAC-S006 | B类膨胀超限 | b_class_inflation_rate | >= | 0.3 | require_approval |

### 4.3 OBAC层级推导

中心级角色可访问其下属部门的数据（如"研发中心"角色可访问"研发一部/二部/三部"的数据）。`l1_b6` 范围通过检查数据的 `l1_code == "B6"` 实现精确过滤。

|------|------|
| 版本快照持久化 | `VersionSnapshotRecord` + SHA256完整性校验 |

### 5.5 图查询引擎

| 查询能力 | 方法 | 说明 |
|---------|------|------|
| 按类型查找 | `find_by_type(type_id, filters)` | 支持属性过滤 |
| 关联查找 | `find_related(instance_id, relation_type, direction, max_depth)` | BFS，支持方向和深度控制 |

### 5.6 启动时一致性检查

`OntologyConsistencyChecker.check_all()` 执行6项检查：

| 检查项 | 严重度 | 说明 |
|--------|--------|------|
| 对象-关系引用 | CRITICAL | 对象的participating_relations中的关系是否存在 |
| 关系源/目标 | CRITICAL | 关系的source_object/target_object是否存在 |
| 反向关系 | HIGH | reverse_relation_id是否有效且反向指回 |
| 场景激活 | HIGH | 场景的activated_objects/rules/behaviors是否都存在 |
| 域内聚 | HIGH | 域的core_objects/core_behaviors是否都存在 |
| 双向一致性 | MEDIUM | 冻结↔释放、对标↔驱动等关系对的互相引用 |

### 5.7 缓存管理

Cache-Aside 模式，Redis + 本地缓存双写。本地缓存支持TTL过期检查。

## 六、如何支撑业务

### 6.1 端到端业务闭环

```
SP/BP战略 → 预算编制 → A/B授予 → 费用报销 → 预警监控 → 经营分析 → PDCA复盘 → 报表出具 → 次年预算
     ↑                                                                                    │
     └──────────────────────────── 反向输入（复盘结论→战略调整）←──────────────────────────┘
```

### 6.2 本体驱动的四大核心能力

#### 能力一：合规底线不可逾越

15条硬规则构成合规底线，任何操作违反硬规则即被阻断。

#### 能力二：预警体系精准分级

20条软规则 + 9个L1专项规则，四色分级（蓝/黄/橙/红），响应时限+自动升级。

#### 能力三：AI推理可追溯

OAG架构确保AI推理过程可追溯：场景匹配→上下文注入→规则校验→幻觉检测→权限管控。

#### 能力四：定义与执行一致

- 对象/关系**实例化**：元数据定义→运行时实例，支持"报销单#001挂载到预算项目#BUD-2024-001"
- 基数**强制执行**：N:1不允许一个报销单挂载多个预算项目
- 行为副作用**结构化**：程序可自动执行副作用（increment/decrement/set/compute）
- 事件**驱动**：本体变更自动触发事件流，下游系统可订阅
- 一致性**校验**：启动时自动检查引用完整性

### 6.3 审批链动态编排

强管控模式下最多9步审批链（5步组织线+4步法人线），实际步数根据条件动态确定。

### 6.4 数据一致性保障

报表引擎内置 `validate_data_consistency()` 方法 + 图查询引擎 `find_path()` 追踪数据血缘。

## 八、设计原则总结

### 8.1 核心原则

1. **定义清晰**：每个对象有自然语言定义，每个关系有业务语义
2. **场景可组合**：场景层预先布好可组合性，大模型从中提取而非凭空发挥
3. **推理可追溯**：规则原子化 + 推理轨迹，每步推理看得见、查得到、能复盘
4. **规则原子化**：一条规则只管一跳，复合效果由大模型组装
5. **参数可调整**：软规则阈值运行时可修改，无需改代码
6. **变更可治理**：影响分析 + 版本快照 + Diff + 血缘 + 真实回滚
7. **健康可度量**：10维度健康度 + 6级成熟度 + 6类技术债扫描
8. **权限可管控**：字段级 + OBAC(层级推导) + ABAC(10种操作符) + AI分级
9. **定义与执行一致**：实例化机制 + 基数强制 + 结构化副作用 + 事件驱动 + 一致性校验
